# 边界条件追根究底式覆盖分析

## 流程总览

```
步骤 1            步骤 2              步骤 3              步骤 4
收集上下文    →   追问分析      →    逐个呈现      →    执行修改
git diff         对每步用 7 问       费曼解释每点        按低→中→高
构建链路         广度 + 深度         方案 + 推荐          分批验证
                 必要时读理论参考     一个一个来
                                     每点等确认
```

**核心原则**：不再随机罗列边界条件，而是沿着本次改动的上下游链路按时间顺序逐层下钻。如需深入理解分析方法背后的理论依据，读 `references/theory-toolbox.md`。

---

## 步骤 1：收集上下文 & 构建链路

### 1.1 获取改动

```bash
git diff --cached --stat && git diff --stat   # 摘要
git diff --cached && git diff                  # 完整 diff
```

从 diff 中提取被修改的函数名、组件名、方法名。

### 1.2 阅读源码确认

对每个改动函数，确认三件事：
- **函数签名**：入参类型、返回值类型、可能抛什么异常
- **调用方**：谁在什么条件下调用它（用 LSP findReferences）
- **消费方**：返回值/副作用被谁依赖、异常会传播到哪

### 1.3 构建三段链路

以改动函数为圆心，向上下游各扩展一层：

```
[上游] 调用方传参 → [核心] 本次改动逻辑 → [下游] 返回值消费 / 异常传播
```

**示例**：改动 `validateFile(file)` 函数中 `>` 改为 `>=`

```
【上游 - 调用方】                    【核心 - validateFile】           【下游 - 消费方】
U1: handleDrop(e) 提取 files[0]  →   C1: if (!file) return error    D1: result.valid 决定是否加入列表
U2: handlePaste(e) 提取 files[0] →   C2: if (size >= MAX) reject ←  D2: FileList 根据 valid 渲染状态
U3: <FileInput onChange={...}>    →   C3: if (!allowed type) reject   D3: 若 throw → 无 catch → 白屏
                                      C4: return { valid: true }
```

**原则**：
- 默认只拆到上下游各一层，不展开全链路（除非发现传播链更长且关键）
- 上游关注参数来源的多样性（不同调用方传的值可能差异很大）
- 核心关注每个分支和状态转换的边界
- 下游关注返回值/异常的传播路径（null 传到哪里会炸？）

> 如果你对"为什么用契约视角分析上下游"、"如何精确列出边界值"、"风险优先级怎么量化"等方法论感兴趣，在分析过程中随时读 `references/theory-toolbox.md`。它包含：契约式设计、边界值分析/等价类划分、FMEA 三维评估、切斯特顿栅栏、混沌工程思维、5 Why 深挖、收益递减定律。

## 步骤 2：追问分析

对链路中的每个步骤（上游每一个调用方、核心每一个分支、下游每一个消费方），做两轮追问。

### 2.1 广度追问（7 个维度，必做）

1. **如果这一步失败了，会怎样？**（主动和被动失败都要考虑）
2. **如果用户在此时做一个异常操作，会怎样？**（快速点击、切换标签、刷新、杀进程）
3. **如果输入数据是极端值，会怎样？**（0、空、负数、超大、特殊字符、二进制）
4. **如果并发执行两次，会怎样？**（重复提交、幂等性）
5. **如果依赖的外部系统异常，会怎样？**（网络、存储、权限、其他服务）
6. **这一步卡住了/超时了，用户能做什么？**（有取消按钮吗？有反馈吗？）
7. **这一步的状态在前端、后端、UI 三者间是否一致？**（数据源唯一性、同步机制）

### 2.2 补充检查维度

| 维度 | 核心问题 |
|------|---------|
| **输入边界** | 空值、极端值、非法值、特殊字符、超长/超大、类型不符 |
| **时序竞态** | 快速连续操作、并发请求、操作未完成又触发了新操作 |
| **状态冲突** | 组件生命周期内状态不一致、多个组件同时操作同一数据 |
| **环境异常** | 网络中断/切换、浏览器兼容、内存不足、存储满 |
| **用户中断** | 中途取消、关闭页面、切换标签、浏览器崩溃恢复 |
| **并发/重复** | 幂等性、去重、重复提交、重试与首次的关系 |
| **UI 边界** | 超长文本截断、大量数据渲染、loading/empty/error 三态 |
| **资源清理** | 内存泄漏、事件监听未解绑、定时器未清除 |

### 2.3 深度下钻（5 Why，按需触发）

当某个边界点的表面修复太简单（"加个 if 判空就行了"），或同一类问题反复出现时，切换到 5 Why 模式追问架构根因。

### 2.4 边界判定

每个步骤追问完后给出明确结论：
- **列入清单**：当前无防护且值得修复
- **不适用**：此风险对此步骤不存在（如同步函数不存在"异步中断"问题，直接跳过）
- **有意设计**：查 git blame 确认是作者故意省略（切斯特顿栅栏），标注跳过
- **不值得修**：低发生度 + 低严重度，收益递减定律建议不修

## 费曼解释原则（贯穿步骤 3 全程）

呈现每个边界点时，必须遵守以下表达原则：

### 核心要求：假设用户对项目了解不深

你的解释要让一个刚接触这个代码库的初级开发者也能完全理解。具体来说：

1. **先说人话，再说代码**：每个边界点先用一句日常语言概括问题本质，然后再展示代码细节。
   - ❌ "C2 步骤的 `>=` 运算符导致 size=0 的 Buffer 通过校验"
   - ✅ "想象你是门卫，只拦身高超过 180cm 的人。现在来了个 0cm 的'隐形人'——你的规则没拦住他，因为 0 确实没超过 180。空文件就是这个'隐形人'。"

2. **用生活类比解释技术概念**：
   - 竞态条件 → "两个人同时编辑同一份文档，后保存的覆盖先保存的"
   - 空指针 → "你给快递员一个空地址，他找不到门牌号"
   - 幂等性 → "电梯按钮：按一次和按十次效果一样"
   - 异常传播 → "多米诺骨牌：一张倒了会推倒后面所有牌"
   - 状态不一致 → "你的购物车显示 3 件，但仓库只备了 2 件"

3. **解释"为什么这是个问题"**：不要只说"这里会出错"，要说清楚出错后的连锁反应，让用户理解后果的严重性。

4. **避免裸用术语**：FMEA、RPN、契约式设计等术语首次出现时必须附带一句话解释。后续使用可以不再解释。

### 自检标准

写完每个边界点的解释后，问自己：
- "如果我妈/我爸/一个非程序员朋友看到这段话，能大概理解问题在哪吗？"
- "我有没有用到某个词，是只有熟悉这个项目的人才懂的？"
- "类比是否准确？有没有过度简化导致误导？"

如果答案不满意，重写直到通俗且准确。

## 步骤 3：逐个呈现边界点与方案

### 3.1 呈现顺序

按复杂度从低到高，**一次只呈现一个边界点**。每个边界点展示完整信息后暂停，等用户确认方案选择，再呈现下一个。

复杂度定义：
- **低**：简单判空/try-catch/防抖，每个 < 30 行
- **中**：状态管理重构/前后端协同校验，每个 30-100 行
- **高**：架构调整/新服务/数据迁移，每个 > 100 行

### 3.2 单个边界点呈现模板

每个边界点必须包含以下所有部分，按顺序输出：

```
---

## 边界点 #N：[简短名称]

### 🔍 通俗解释（费曼区）

[用一段生活类比或通俗语言解释这个问题的本质。
假设读者完全不了解这个项目，用日常场景类比让问题一目了然。
这段解释要让人读完就"哦——原来是这个问题！"]

### 当前行为 vs 预期行为

- **现在会怎样**：[代码实际做了什么，用大白话描述]
- **应该怎样**：[理想情况下应该怎么做]

### 风险评估

用三个维度打分（每项 1-5 分）：

| 维度 | 含义 | 分数 |
|------|------|------|
| 严重度 | 出了问题后果有多严重？（1=无感，5=白屏/数据丢失） | X |
| 发生频率 | 用户踩坑的概率有多大？（1=几乎不可能，5=每次必踩） | X |

**风险值** = 三项相乘 = **XX**
（≥60 必须修 | 30-59 本迭代修 | 15-29 下迭代修 | <15 顺手改或不修）

### 用户怎么踩坑的（触发场景）

### 方案对比

#### 方案 A：[方案名称]
- **思路**：[用通俗语言解释这个方案在做什么]
- **优点**：...
- **缺点**：...
- **改动量**：X 文件 / ~X 行

#### 方案 B：[方案名称]
- **思路**：...
- **优点**：...
- **缺点**：...
- **改动量**：X 文件 / ~X 行

### 🏆 我的推荐：方案 X

**推荐理由**：[用通俗语言解释为什么推荐这个方案，让不了解项目的人也能理解这个决策的合理性]

> ⏸️ **请选择方案（A / B / 或提出你的想法）。确认后我展示下一个边界点。**
```

### 3.3 呈现节奏

- 每展示完一个边界点，**必须暂停等待用户确认**，不得自动跳到下一个
- 用户确认后，简短回应并立即呈现下一个边界点
- 同一复杂度的所有边界点都确认后，输出该段汇总：

> 📋 **[低/中/高]复杂度边界点共 N 个，已全部确认。回复"[低/中/高]复杂度批准"进入下一段。**

- 必须等待批准后才进入下一复杂度段。全部三段批准后才进入步骤 4。

### 3.4 全部确认后的汇总表格

所有边界点都确认后，输出全局汇总：

| # | 步骤 | 边界点 | 严重度 | 发生频率 | 发现难度 | 风险值 | 选定方案 | 复杂度 |
|---|------|--------|--------|---------|---------|--------|---------|--------|
| 1 | C2 | 空文件被放行 | 3 | 3 | 5 | 45 | A | 低 |
| 2 | D3 | 异常致白屏 | 4 | 2 | 4 | 32 | B | 中 |

## 步骤 4：执行修改

按低 → 中 → 高顺序修改。每完成一批，告知用户可手动验证，再继续下一批。

优先修改风险值高的边界点，同复杂度内按风险值降序处理。

## 完整示例

> 任务："修复 validateFile 大小校验 bug：file.size > MAX_SIZE 改为 >="

**步骤 1**：`git diff --cached` → 改动 `validateFile` 一行。LSP 找引用 → 3 个上游调用方，2 个下游消费路径。构建三段链路（见上文 1.3 示例）。

**步骤 2**：对 C1（判空）、C2（大小比较）、D3（异常传播）各走 7 问。

- C1：已有判空，假 File 对象（mock）低概率低后果，→ 不列入
- C2：边界值修复已正确 ✅。追问发现 0 字节文件被放行 → 列入。追问发现 MAX_SIZE 常量可被误改 → 列入。
- D3：caller 无 try-catch，内部 throw 则白屏 → 列入。

**步骤 3**：按复杂度从低到高，逐个呈现边界点。

## 边界点 #1：C2 - 空文件（0 字节）能通过校验

### 🔍 通俗解释

想象你是门卫，只拦身高**超过** 180cm 的人。现在来了个身高 0cm 的"隐形人"——你的规则没拦住他，因为 0 确实没超过 180。

空文件就是这个"隐形人"。代码只检查了"文件是否超过最大限制"，但忘了检查"文件是不是根本没有内容"。一个 0 字节的文件通过了所有检查，被当成正常文件上传了。

### 当前行为 vs 预期行为

- **现在会怎样**：0 字节文件通过校验，被正常上传到服务器，用户得到一个空文件
- **应该怎样**：在上传前就拦截，告诉用户"这个文件是空的，请检查后重试"

### 风险评估

| 维度 | 含义 | 分数 |
|------|------|------|
| 严重度 | 功能受阻但可绕过（用户重新选文件即可） | 3 |
| 发生频率 | 非正常操作路径（偶尔会误选空文件） | 3 |
| 发现难度 | 目前没有任何检查，完全靠用户自己发现 | 5 |

**风险值** = 3 × 3 × 5 = **45**（本迭代修）

### 用户怎么踩坑的

用户上传头像，不小心选了一个空文件（比如刚创建还没写入内容的 .txt）。系统显示"上传成功"，但头像位置一片空白。用户困惑："我明明上传了文件啊？"

### 方案对比

#### 方案 A：直接拒绝空文件
- **思路**：在校验函数开头加一行检查，文件是 0 字节就直接返回错误
- **优点**：改动最小（3 行），逻辑清晰，"空文件 = 无效文件"规则明确
- **缺点**：如果未来需要允许空文件（极罕见），需要改这里
- **改动量**：1 文件 / ~3 行

#### 方案 B：允许上传但给出警告
- **思路**：空文件也能上传，但弹一个确认框提醒用户"这是空文件，确定要上传吗？"
- **优点**：更灵活，给用户选择权
- **缺点**：需要改 UI 层加确认弹窗，改动较大；99% 的情况下空文件是误操作，多一步确认反而烦人
- **改动量**：3 文件 / ~15 行

### 🏆 我的推荐：方案 A

**推荐理由**：空文件 99% 是误操作（选错了文件），直接拒绝最简单也最符合直觉。就像 ATM 机不会让你存一张白纸进去——它直接告诉你"这不是钞票"。

## 边界点 #2：C2 - MAX_SIZE 常量可被误改且无人发现

### 🔍 通俗解释

想象限速牌上的"60"是用铅笔写的——任何人都能偷偷改成"160"，而且没人会注意到。

`MAX_SIZE` 这个常量就是那个限速牌。它定义了文件最大允许多少字节。虽然代码里写着"常量"（不允许改），但实际上如果有人不小心改了它的值（比如把 10MB 改成了 10 字节），没有任何测试会报错——系统会悄悄开始拒绝所有正常文件，而没人知道为什么。

### 当前行为 vs 预期行为

- **现在会怎样**：常量值可被任意修改，没有自动化检查，直到用户投诉"为什么我的文件传不上去"才被发现
- **应该怎样**：有单元测试守护常量值的合理范围，改错了立刻在 CI 阶段报错

### 风险评估

| 维度 | 含义 | 分数 |
|------|------|------|
| 严重度 | UI 异常但不影响核心功能（改回来就好） | 2 |
| 发生频率 | 需刻意构造（正常开发不会改常量） | 1 |
| 发现难度 | 写个单测就能立刻发现 | 2 |

**风险值** = 2 × 1 × 2 = **4**（顺手改或不修）

### 用户怎么踩坑的

新来的实习生重构代码时，把 `MAX_SIZE = 10 * 1024 * 1024`（10MB）误改成了 `MAX_SIZE = 10 * 1024`（10KB）。没人注意到，直到一周后用户投诉"为什么 50KB 的头像传不上去"。

### 方案对比

#### 方案 A：写单元测试守护常量范围
- **思路**：写一个测试断言 `MAX_SIZE` 必须在合理范围内（比如 1MB-100MB），改错了测试就红
- **优点**：开发期就能拦截，成本最低；测试本身就是文档，告诉后来者这个值的合理范围
- **缺点**：需要维护测试中的合理范围值
- **改动量**：1 文件 / ~10 行

#### 方案 B：运行时校验常量值
- **思路**：应用启动时检查 `MAX_SIZE` 是否在合理范围，不合法就报错阻止启动
- **优点**：双重保险
- **缺点**：配置错误是开发期问题，运行时检查太晚了；增加了启动逻辑复杂度
- **改动量**：1 文件 / ~5 行

### 🏆 我的推荐：方案 A

**推荐理由**：这是开发期产生的 bug，最低成本的拦截点就是单元测试。就像在工厂流水线上装质检——在产品出厂前发现问题，远比等顾客投诉再处理便宜得多。

## 边界点 #3：D3 - 校验函数抛异常导致整个页面白屏

### 🔍 通俗解释

想象你在玩叠叠乐（Jenga），校验函数是中间的一块积木。如果这块积木突然被抽走（抛出异常），它上面的所有积木（整个页面）都会塌下来。

现在的问题是：`validateFile` 函数在遇到异常时会"扔出一个错误"（throw），但调用它的代码没有"接住"这个错误（没有 try-catch）。结果就是错误一路向上传播，最终导致整个页面崩溃白屏——用户看到的是一个空白页面，什么操作都做不了。

这就像多米诺骨牌：一张倒了（校验出错），后面所有牌都跟着倒（整个应用崩溃），因为中间没有任何"挡板"来阻止连锁反应。

### 当前行为 vs 预期行为

- **现在会怎样**：校验函数抛出异常 → 调用方没捕获 → 异常冒泡到顶层 → 整个页面白屏
- **应该怎样**：校验失败时优雅降级，显示错误提示，页面其他功能照常可用

### 风险评估

| 维度 | 含义 | 分数 |
|------|------|------|
| 严重度 | 核心流程中断（整个页面不可用） | 4 |
| 发生频率 | 正常路径偶尔触发（上传特殊文件时） | 2 |
| 发现难度 | 线上监控能发现（白屏有错误日志） | 4 |

**风险值** = 4 × 2 × 4 = **32**（本迭代修）

### 用户怎么踩坑的

用户上传一个文件名包含特殊字符的文件（比如 `报告<最终版>.docx`），校验函数解析文件名时出错抛出异常。由于没有错误捕获，整个上传页面变成白屏。用户不得不刷新页面，之前填写的表单数据全部丢失。

### 方案对比

#### 方案 A：在每个调用方处加 try-catch
- **思路**：找到所有调用 `validateFile` 的地方（3 处），每处都包一层 try-catch
- **优点**：直接明了，哪里调用哪里负责
- **缺点**：同样的错误处理代码写 3 遍，未来新增调用方容易忘记加 try-catch
- **改动量**：1 文件 / ~30 行

#### 方案 B：封装一个"安全版"校验函数
- **思路**：创建一个 `safeValidateFile()` 函数，内部调用原函数并统一捕获异常，保证"永远不会抛出异常"。所有调用方改用这个安全版
- **优点**：错误处理集中在一处，新增调用方直接用安全版，不会遗漏；"这个函数永远不会抛异常"是一个简单可靠的承诺
- **缺点**：多了一层封装，需要理解两层函数
- **改动量**：2 文件 / ~20 行

### 🏆 我的推荐：方案 B

**推荐理由**：集中防护优于分散重复。3 个地方写 3 遍相同的 try-catch，不如把防护做在一处。就像大楼不会给每个房间配一个消防栓——而是在每层楼的固定位置统一配置，确保不遗漏。

## 执行准则

1. **范围默认 ±1 层**：上游到调用方，下游到消费方，不蔓延全链路。
2. **先看代码再分析**：必须读源码确认行为，不靠猜测。
3. **不跳过追问**：每步走完 7 问才做边界判定。
4. **果断跳过**：追问后确认不存在风险，直接标"不适用"，不硬凑。
5. **不跨点推进**：一个边界点未确认不展示下一个。每次只呈现一个边界点，等用户确认方案后再继续。
6. **不替用户做决定**：给 2-3 个方案 + 推荐理由，用户拍板。
7. **知道何时停**：风险值 < 15 的边界可直接标"不修复"。
8. **方法参考**：分析卡住时，读 `references/theory-toolbox.md` 找灵感——它告诉你怎么契约分析、怎么列精确边界值、怎么五问挖根因。
9. **费曼原则**：每个边界点的解释必须通俗易懂，用生活类比让不了解项目的人也能理解问题本质。写完解释后自检：非程序员能看懂吗？（详见"费曼解释原则"章节）
