# Spec / Plan 审查与完善

## 概述

在动手实施之前，让一个"实施者视角"的 subagent 通读整份 spec/plan，以"我要一次性把这个系统构建出来"的心态找出所有疑问、模糊之处和缺失要素。拿到 subagent 返回的疑惑清单后，不急于修改文档，而是先通过测试验证能验证的部分，再针对每个疑惑点设计多种解决方案，按复杂度分批呈现给用户，逐段获得批准后才落笔修改。

这样做的原因：直接修改文档容易遗漏深层问题；先让独立视角审视、再系统性地解决每个问题，能让最终的 spec/plan 真正可执行。

**开始时宣布：**"我正在使用 spec-plan-reviewer skill 审查并完善这份 spec/plan。"

---

## 流程总览

```
步骤 1              步骤 2              步骤 3              步骤 4
确认文档        →   调用 subagent   →   逐段呈现方案   →   修改文档
(已在上下文/文件)   获取疑惑清单        测试 + 多方案        全部批准后
                    (实施者视角)        逐段批准             才动笔
```

---

## 步骤 1：确认目标文档与收集上下文

### 1.1 确认目标文档

spec/plan 的来源有两种情况：
- **已在上下文中**：刚刚由本会话生成（如通过 brainstorming skill），内容已在对话历史里，无需重新读取。记录其文件路径（如果已保存到文件）供 subagent 使用。
- **存在于文件中**：用户指定了文件路径，记录下来供 subagent 读取。

无论哪种情况，最终需要拿到 spec/plan 文件的**绝对路径**，传给 subagent 让它自己读取。

### 1.2 收集项目上下文（可选）

如果上下文中还没有足够的项目信息，快速收集：
- 项目结构（`ls` 或 `find` 快速扫描）
- 已有的测试文件（了解测试覆盖现状）
- 依赖的技术栈（`package.json`、`requirements.txt` 等）
- 已知的约束条件（用户提到的限制、时间要求等）

---

## 步骤 2：调用 Subagent 审查

### 2.1 构建 subagent 提示词

使用 `references/reviewer-prompt.md` 中的模板构建 subagent 提示词。核心角色设定：

> 你是一名负责一次性完成此 spec/plan 实施工作的 AI。在开始之前，你有什么疑问吗？有哪些地方不明确？要成功构建这个系统，还有哪些要素是缺失的？

### 2.2 调用 subagent

通过 Agent 工具调用 subagent，传入 spec/plan 文件的**绝对路径**和项目上下文信息。subagent 自行读取文件内容，不需要在提示词中内联全文。

subagent 应当返回结构化的疑惑清单，每个疑惑点包含：
- **编号**：唯一标识
- **类别**：`模糊不清` / `要素缺失` / `逻辑矛盾` / `技术风险` / `边界未定义`
- **通俗解释**：用日常语言 + 生活类比说明这个问题是什么（费曼学习法）
- **描述**：具体的技术问题是什么
- **所以呢**：如果不解决，会导致什么用户能感知到的具体麻烦
- **涉及位置**：spec/plan 中的哪个章节或段落

### 2.3 整理疑惑清单

收到 subagent 反馈后，对疑惑点做二次整理：
- 合并重复或高度相似的点
- 按复杂度排序：低 → 中 → 高
- 标注哪些可以通过运行测试直接验证
- **检查费曼解释质量**：如果某个疑惑点的通俗解释仍然充满行话、或类比不贴切，在此阶段改写为更易懂的表述，确保用户无需技术背景也能理解问题所在

将整理后的清单呈现给用户，告知："以下是审查发现的 N 个疑惑点，我将按复杂度从低到高逐一为你分析并提出方案，每段确认后再继续下一段。"

---

## 步骤 3：逐段呈现方案

这是整个流程的核心。对每个疑惑点（或按复杂度分组后的一组相关疑惑点），执行以下子流程：

### 3.1 能测试的先测试

如果疑惑点涉及可以通过代码验证的问题（如"这个 API 是否支持 X 参数"、"当前数据库 schema 是否兼容 Y 场景"），先编写并运行快速测试：

```bash
# 示例：验证 API 行为
node -e "const lib = require('./lib'); console.log(lib.someMethod('test-case'))"
```

将测试结果作为方案设计的依据，而不是凭空猜测。

### 3.2 设计 2-3 种方案

针对每个疑惑点，设计 2-3 种解决方案，每种方案包含：

| 要素 | 说明 |
|------|------|
| 方案名称 | 简短有辨识度 |
| 核心思路 | 一两句话说明怎么做 |
| 优点 | 这个方案的长处 |
| 缺点 | 这个方案的短处和风险 |
| 实施成本 | 大致工作量（小/中/大） |
| 适用场景 | 什么情况下最适合用这个方案 |

最后给出**推荐方案**及推荐理由。

### 3.3 用费曼学习法描述疑惑点

每个疑惑点的描述必须遵循费曼学习法原则：**假设用户对项目的技术细节了解不深，用他能看懂的话术来解释**。具体做法：

- **不用行话开头**：先用日常语言说清楚"这件事是什么"，再补充技术术语
- **用类比打桥**：把抽象的技术问题比作生活中熟悉的事物（如把数据库连接池比作餐厅座位、把缓存比作便签纸）
- **说清楚"所以呢"**：不只说"这里没有定义"，要说明"这会导致什么具体的麻烦"，让用户感受到问题的实际影响
- **检验标准**：如果一个不了解代码的人读完描述后能说出"哦，这个问题就是……"，说明解释到位了

### 3.4 按复杂度分段呈现

将方案按复杂度分批呈现给用户，每批结束后明确询问：

**呈现格式示例：**

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔍 疑惑点 #1 [低复杂度]：数据库连接池配置未指定
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【通俗解释】
想象你开了一家餐厅，但没规定店里有多少张桌子。
如果客人（请求）来得太多，没有桌子就只能排队等着，
甚至直接被拒之门外。数据库连接池就是"桌子数量"的设定。

【问题】spec 中未说明连接池大小、超时时间等参数。
【所以呢】实施时只能靠猜测设一个数字，
          猜小了用户会卡，猜大了服务器会撑爆。

── 方案 A：使用框架默认值 ──────────────
核心思路：不做额外配置，依赖 ORM/数据库驱动的默认参数
优点：零配置成本，快速推进
缺点：默认值不一定适合生产负载
实施成本：小
适用场景：原型阶段或低流量服务

── 方案 B：基于预期负载计算 ────────────
核心思路：根据预估 QPS 和响应时间计算合理连接池大小
优点：有据可依，更贴合实际
缺点：需要负载预估数据，初期可能不准
实施成本：中
适用场景：有明确性能目标的场景

── 方案 C：配置为环境变量 + 压测校准 ──
核心思路：参数外置为环境变量，上线后通过压测逐步调优
优点：灵活可调，不硬编码
缺点：需要配套压测流程
实施成本：中
适用场景：生产级服务

✅ 推荐：方案 C — 兼顾灵活性和可运维性

请问是否同意采用方案 C？或者你有其他偏好？
（确认后我将继续下一个疑惑点）
```

### 3.5 等待用户批准

每个疑惑点（或一组）呈现后，**必须等待用户明确批准**才能继续下一个。

如果用户：
- **同意推荐方案**：记录决策，继续下一个
- **选择其他方案**：记录用户选择，继续下一个
- **提出修改意见**：根据意见调整方案，重新呈现
- **要求跳过**：标注为"用户决定延后处理"，继续下一个

---

## 步骤 4：修改文档

### 4.1 前置条件

**只有当所有疑惑点都获得用户批准（或被明确标记为延后处理）后，才能开始修改 spec/plan 文档。**

这是硬性约束。在此之前，文档保持原样不动。

### 4.2 执行修改

根据每个疑惑点的批准方案，修改 spec/plan 文档：

- 在对应章节补充缺失内容
- 修正模糊表述为精确描述
- 添加必要的约束条件和边界说明
- 如有需要，新增章节（如"连接池配置"、"错误处理策略"等）

### 4.3 标注修改来源

每处修改旁用注释标注来源，便于追溯：

```markdown
<!-- [审查补充] 疑惑点 #3：连接池配置 -->
连接池参数配置如下：
- 最大连接数：20（通过环境变量 DB_POOL_MAX 覆盖）
- 连接超时：30s
- 空闲超时：300s
```

### 4.4 呈现修改摘要

修改完成后，向用户呈现一份简短摘要：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✅ 文档修改完成
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

共处理 N 个疑惑点：
  ✅ 已解决：X 个
  ⏸️  延后处理：Y 个

主要修改：
  1. [章节名] 补充了 XXX
  2. [章节名] 明确了 YYY
  3. [章节名] 新增了 ZZZ

文件已保存至：<路径>
```

## 注意事项

### 不要跳过测试验证

当疑惑点可以通过运行代码验证时，先跑测试再设计方案。实测结果比推理更可靠，也能帮助设计出更准确的方案。

### 不要一次性倾倒所有方案

分段呈现是为了让用户有节奏地审批，避免信息过载。每次呈现 1-3 个相关疑惑点即可。

### 不要未经批准就修改文档

这是此 skill 最核心的约束。无论疑惑点看起来多么简单、方案多么显而易见，都要等用户点头后才动文档。用户的判断可能有你看不到的上下文。

### 尊重用户的方案选择

推荐方案只是你的建议。用户选择其他方案时，不要试图说服，直接记录并执行。
