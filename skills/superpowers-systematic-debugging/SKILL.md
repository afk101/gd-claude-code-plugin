# 系统化调试

## 概述

随机修复浪费时间并产生新的 bug。快速补丁掩盖了根本问题。

**核心原则：** 在尝试修复之前必须找到根本原因。仅修复症状是失败的。

**违反此流程的字面意思就是违反调试的精神。**

## 铁律

```
没有根本原因调查就不能修复
```

如果你还没有完成 Phase 1，就不能提出修复方案。

## 使用时机

用于任何技术问题：
- 测试失败
- 生产环境中的 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**特别适用于以下情况：**
- 时间紧迫（紧急情况会让猜测变得诱人）
- "只需一个快速修复"似乎很显然
- 你已经尝试了多种修复方案
- 之前的修复没有奏效
- 你没有完全理解这个问题

**不要跳过的情况：**
- 问题看起来很简单（简单的 bug 也有根本原因）
- 你很着急（匆忙会导致返工）
- 经理要求立即修复（系统化比盲目尝试更快）

**与 brainstorming / writing-plans 的关系：**

systematic-debugging 是**调查阶段**，不写修复代码。调查清楚根本原因后，顺序是：

```
systematic-debugging → brainstorming → writing-plans → 实现
```

- **systematic-debugging**：调查根本原因，过程中向用户提问收集信息，更新 findings
- **brainstorming**（根本原因明确后）：与用户讨论修复方案，产出 spec；有新发现则追加到已有 findings，不新建
- **writing-plans**（方案确定后）：制定具体修复计划
- **实现**：按 plan 写测试、写修复、验证

## 四个阶段

必须完成每个阶段后才能进入下一个阶段。

### Phase 1: 根本原因调查

**在尝试任何修复之前：**

0. **创建 findings 文件** — 立即在 `docs/superpowers/findings/YYYY-MM-DD-<topic>-findings.md` 创建，贯穿整个调查过程持续更新。**每执行 2 次查看 / 搜索 / 运行操作后必须更新。**

   findings 文件记录的内容包括但不限于：
   - 用户提供的第一手信息（现象描述、复现步骤、预期行为）
   - 自己的调查发现（git 历史、错误堆栈、代码阅读、日志分析、组件状态）
   - 每次形成的假设及验证结果
   - 排除的方向及理由
   - 最终确认的根本原因

   **findings 不只是问答记录，更是完整的调查日志。** 调查的每一步发现都应该写进去，不要只记用户说的，自己查到的同样重要。

1. **向用户提问，收集第一手信息**

   调查开始前，逐一向用户提问，把回答记入 findings。**只问用户才能回答的问题**，代码层面的事实（git 历史、日志、配置）自己去查，不要反问用户：

   - bug 的具体现象是什么？（错误信息、截图、日志片段）
   - 如何复现？（操作步骤、触发条件）
   - 预期行为是什么？（正确的结果应该是什么样的）
   - 影响范围有多大？（所有用户 / 特定条件 / 偶发）

   **提问原则：一次一个问题，等用户回答后再提下一个。** 不要一次性抛出所有问题。

   调查过程中若遇到业务层面的信息盲区，随时继续追问：
   - "这个行为在 X 情况下也会出现吗？"
   - "之前这个功能是怎么工作的？"
   - "这个字段的预期取值范围是什么？"

   **不要问用户的事情（自己查）：**
   - 最近有哪些代码变更 → `git log`、`git diff`
   - 报错发生在哪个文件 → 读堆栈跟踪
   - 依赖版本是什么 → 查 package.json / lockfile
   - 配置是怎么设置的 → 读配置文件

2. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪（stack traces）
   - 记录行号、文件路径、错误代码

3. **一致地复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 它每次都发生吗？
   - 如果无法复现 → 向用户追问更多细节，不要猜测

4. **检查最近的变更**
   - 什么变更可能导致这个问题？
   - Git diff、最近的提交
   - 新的依赖、配置变更
   - 环境差异

5. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → build → signing, API → service → database）：**

   **在提出修复之前，添加诊断检测：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播
     - 检查每一层的状态

   运行一次以收集证据，显示在哪里中断
   然后分析证据以识别失败的组件
   然后调查该特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层失败（secrets → workflow ✓, workflow → build ✗）

6. **追踪数据流**

   **当错误位于调用栈（call stack）深处时：**

   参见本目录中的 `root-cause-tracing.md` 以了解完整的反向追踪技术。

   **快速版本：**
   - 错误值来自哪里？
   - 是什么用错误的值调用了这个？
   - 继续向上追踪直到找到源头
   - 在源头修复，而不是在症状处

### Phase 2: 模式分析

**在修复之前找到模式：**

1. **找到可工作的示例**
   - 在同一代码库中定位类似的可工作代码
   - 什么是可工作的且类似于已损坏的？

2. **与参考实现对比**
   - 如果实现模式，完整阅读参考实现
   - 不要浏览 - 阅读每一行
   - 在应用之前完全理解模式

3. **识别差异**
   - 可工作和损坏之间有什么不同？
   - 列出每个差异，无论多小
   - 不要假设"那不重要"

4. **理解依赖关系**
   - 这需要哪些其他组件？
   - 什么设置、配置、环境？
   - 它做了哪些假设？

### Phase 3: 假设与测试

**科学方法：**

1. **形成单一假设**
   - 清晰陈述："我认为 X 是根本原因，因为 Y"
   - 写入 findings 文件的"技术决策"部分，记录假设及理由
   - 要具体，不要模糊

2. **最小化测试**
   - 做最小的可能变更来测试假设
   - 一次一个变量
   - 不要一次修复多个事情

3. **在继续之前验证**
   - 有效吗？是的 → 根本原因已确认，进入 brainstorming 讨论修复方案
   - 无效？形成新假设
   - 不要在上面添加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 更多研究

### Phase 4: 实现

**根本原因确认后，不要在此直接写修复代码。** 统一走以下流程：

```
brainstorming → writing-plans → subagent-driven-development
```

- **brainstorming**：与用户讨论修复方案，产出 spec；有新发现则追加到已有 findings
- **writing-plans**：基于 spec 制定具体修复计划，用户确认后执行
- **subagent-driven-development**：按 plan 派遣 subagent 实现修复（内部遵循 test-driven-development）

如果修复尝试失败：
   - 停止
   - 计数：你已经尝试了多少次修复？
   - 如果 < 3：返回 Phase 1，用新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见下面的第 5 步）**
   - 不要在没有架构讨论的情况下尝试修复 #4

5. **如果 3 次以上修复失败：质疑架构**

   **指示架构问题的模式：**
   - 每次修复在不同的地方揭示新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每次修复在其他地方创建新症状

   **停止并质疑基础：**
   - 这个模式根本上是合理的吗？
   - 我们是否"仅凭惯性坚持使用它"？
   - 我们应该重构架构还是继续修复症状？

   **在尝试更多修复之前与你的合作伙伴讨论**

   这不是失败的假设 - 这是错误的架构。

## 危险信号 - 停止并遵循流程

如果你发现自己在想：
- "暂时快速修复，稍后调查"
- "只是尝试更改 X 看看是否有效"
- "添加多个更改，运行测试"
- "跳过测试，我会手动验证"
- "可能是 X，让我修复它"
- "我不完全理解但这可能有效"
- "模式说 X 但我会以不同方式适应"
- "这是主要问题：[列出修复方案而没有调查]"
- 在追踪数据流之前提出解决方案
- **"再尝试一次修复"（当已经尝试 2 次以上时）**
- **每次修复在不同地方揭示新问题**

**所有这些都意味着：停止。返回 Phase 1。**

**如果 3 次以上修复失败：** 质疑架构（见 Phase 4.5）

## 你的合作伙伴发出你做错了的信号

**注意这些重定向：**
- "那没有发生吗？" - 你没有验证就假设了
- "它会显示我们...？" - 你应该添加证据收集
- "停止猜测" - 你在不理解的情况下提出修复
- "深入思考这个" - 质疑基础，而不仅仅是症状
- "我们卡住了？"（沮丧）- 你的方法不起作用

**当你看到这些时：** 停止。返回 Phase 1。

## 常见的合理化借口

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要流程" | 简单问题也有根本原因。流程对于简单的 bug 来说很快。 |
| "紧急情况，没有时间流程" | 系统化调试比猜测和检查的盲目尝试更快。 |
| "先尝试这个，然后调查" | 第一次修复设定了模式。从头开始就做对。 |
| "我会在确认修复有效后编写测试" | 未测试的修复不会持久。先测试证明它。 |
| "一次多个修复节省时间" | 无法隔离什么有效。导致新 bug。 |
| "参考太长，我会适应模式" | 部分理解保证会有 bug。完整阅读它。 |
| "我看到问题了，让我修复它" | 看到症状 ≠ 理解根本原因。 |
| "再尝试一次修复"（在 2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，不要再次修复。 |

## 快速参考

| Phase | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 向用户提问、阅读错误、复现、检查变更、收集证据 | 理解什么和为什么 |
| **2. 模式** | 找到可工作的示例、对比 | 识别差异 |

## 当流程揭示"没有根本原因"时

如果系统化调查揭示问题确实是环境性的、时间依赖的或外部的：

1. 你已经完成了流程
2. 将调查结论记录到 findings 文件并提交
3. 实现适当的处理（重试、超时、错误消息）
4. 添加监控/日志以供未来调查

**但是：** 95% 的"没有根本原因"案例是调查不完整。

## 支持技术

这些技术是系统化调试的一部分，可在本目录中找到：

- **`root-cause-tracing.md`** - 通过调用栈反向追踪 bug 以找到原始触发点
- **`defense-in-depth.md`** - 在找到根本原因后在多层添加验证
- **`condition-based-waiting.md`** - 用条件轮询替换任意超时

**相关 skills（调查完成后依次调用）：**
- **superpowers:brainstorming** - 根本原因明确后，与用户讨论修复方案，产出 spec
- **superpowers:writing-plans** - 方案确定后，制定具体修复计划
- **superpowers:test-driven-development** - 按 plan 写复现失败测试，再写修复
- **superpowers:verification-before-completion** - 声称修复完成前验证无回归

## 现实世界的影响

来自调试会话：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时的盲目尝试
- 首次修复率：95% vs 40%
- 引入的新 bug：接近零 vs 常见
